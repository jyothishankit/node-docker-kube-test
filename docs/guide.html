PART 1

Dockerfiles

Mental model

How Docker reads a Dockerfile

Three ideas explain almost every decision in the two Dockerfiles.

Instructions become layers

FROM, RUN, COPY run top to bottom. Each one that changes files stacks a read-only layer; the image is all layers combined.

Layers are cached

A rebuild reuses a layer if its instruction and inputs are unchanged. Once one layer changes, every layer below it rebuilds.

FROM node:22-alpine · cached COPY package*.json · cached RUN npm ci · cached COPY server.js · rebuilt

The build context

docker build ./backend sends that folder to the builder, minus what .dockerignore excludes. COPY can only see files in the context.

backend/Dockerfile

The backend: a two-stage build

This file has two FROM lines, so it's a multi-stage build. Only the last stage becomes the image. The first stage exists to produce node_modules and is then thrown away.

backend/Dockerfile

# Install dependencies with npm in a throwaway stage...
FROM node:22-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev

# ...then run on plain Alpine with its Node.js package (no npm, yarn or
# corepack), which is much smaller than the official node image.
FROM alpine:3.20
RUN apk add --no-cache nodejs && addgroup -S app && adduser -S app -G app
WORKDIR /app
ENV NODE_ENV=production
COPY --from=deps /app/node_modules ./node_modules
COPY package.json server.js ./
USER app
EXPOSE 5000
CMD ["node", "server.js"]
  • 2

    FROM picks the base image: Node 22 on Alpine Linux. AS deps names the stage so line 13 can copy from it.

  • 3

    WORKDIR sets the current directory for later instructions and creates it if needed. It's a mkdir -p /app && cd /app that persists.

  • 4–5

    The key caching trick for Node images. Copy only the manifest, install, and copy the code later. Editing server.js leaves the manifest unchanged, so the slow npm ci layer comes from cache and rebuilds take seconds. If you ran COPY . . first, every code edit would reinstall all dependencies.

    npm ci installs the exact versions in package-lock.json, fails if the lockfile and package.json disagree, and starts from a clean node_modules. --omit=dev skips devDependencies.

  • 9

    Stage 2 starts again from bare Alpine (about 7 MB). Nothing from stage 1 carries over unless it's copied. node:22-alpine also ships npm, yarn, corepack and headers that a running server doesn't need.

  • 10

    apk is Alpine's package manager; --no-cache avoids keeping its index in the layer. addgroup -S / adduser -S create a system user for line 15. The steps are chained with && into one RUN, so they make one layer. A file deleted in a later layer still takes space in the earlier one.

  • 12

    ENV sets a variable baked into the image and every container from it. NODE_ENV=production switches Express and other libraries out of debug mode.

  • 13

    COPY --from=deps reaches into the earlier stage and takes only its output. That's the payoff: the dependencies arrive without the tools that installed them.

  • 14

    The app code comes last because it changes most often.

  • 15

    USER app makes the container run without root. Someone who exploits the app doesn't get root inside the container.

  • 16

    EXPOSE is documentation only. It doesn't open or publish anything. Publishing happens through docker run -p, Compose ports:, or a Kubernetes Service.

  • 17

    CMD is the default start command. It uses the exec form (a JSON array). The next table shows why that matters.

Exec form vs. shell form

FormExampleWhat runs as PID 1SIGTERM reaches Node?
ExecCMD ["node","server.js"]node itselfYes
ShellCMD node server.js/bin/sh -c "…"Usually not; sh doesn't forward it

When Kubernetes stops a pod it sends SIGTERM. server.js handles it: it stops accepting connections, finishes in-flight requests and disconnects from MongoDB. That only works because the exec form delivers the signal straight to Node.

frontend/Dockerfile

The frontend: build with Node, serve with nginx

Once built, a React app is plain HTML, JS and CSS. Node is only needed to build it, so the final image is nginx plus about 150 KB of files.

frontend/Dockerfile

FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# alpine-slim is the smallest official nginx image (~12 MB).
FROM nginx:1.27-alpine-slim
COPY nginx.conf /etc/nginx/nginx.conf
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
  • 3–4

    Same cache-friendly order as the backend. Here the full install is needed, because Vite, the build tool, is a devDependency.

  • 5

    COPY . . copies the whole context. Because .dockerignore lists node_modules, your Mac's macOS-built modules never overwrite the Linux ones from line 4.

  • 6

    Vite writes the optimised static site to /app/dist.

  • 10

    This replaces nginx's main config. Owning that file is what allows worker_processes 2; the default auto starts one worker per host CPU, which meant 18 on this Mac.

  • 11

    Only the built files cross into the final image.

  • —

    There's no CMD. It's inherited from the base image, which already runs nginx -g 'daemon off;'. Anything you don't override comes from the parent image.

.dockerignore

Keep the build context small

backend/.dockerignore

It works like .gitignore for the build context. Builds are faster because 40 MB of node_modules is never sent to the builder. They're also correct, because no wrong-platform binaries get copied in.

PART 2

Kubernetes

Every manifest

The same four parts, every time

shape of any manifest

apiVersion: apps/v1   # which API group/version defines this kind
kind: Deployment      # what object this is
metadata:             # identity: name, namespace, labels
spec:                 # the desired state you want to exist

You declare the desired state. Controllers in the cluster continuously work to make reality match it. Autoscaling is one of those controllers changing a number in that desired state for you.

k8s/20-backend.yaml

The backend Deployment

k8s/20-backend.yaml Deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: crud-app
  labels: { app: backend }
spec:
  # No `replicas` field: the HorizontalPodAutoscaler owns the replica count,
  # so re-applying this manifest won't reset a scaled-out deployment.
  selector:
    matchLabels: { app: backend }
  template:
    metadata:
      labels: { app: backend }
    spec:
      terminationGracePeriodSeconds: 20
      containers:
        - name: backend
          image: crud-backend:latest
          imagePullPolicy: IfNotPresent # image is loaded into minikube by deploy.sh
          ports:
            - containerPort: 5000
          env:
            - name: PORT
              value: "5000"
            - name: MONGO_URI
              value: mongodb://mongo:27017/crud
            - name: MAX_ITEMS # cap on stored items, keeps the DB to ~1 MB
              value: "500"
            - name: MONGO_POOL_SIZE # x 5 pods = at most 15 DB connections
              value: "3"
            # Keep the V8 heap small so the pod fits in its 50Mi limit.
            - name: NODE_OPTIONS
              value: --max-old-space-size=24 --max-semi-space-size=2
          # The HPA computes utilization as a percentage of the CPU *request*,
          # so the request must be set. A small request keeps scaling easy to
          # trigger on a laptop. Memory and scratch disk are capped at 50Mi.
          resources:
            requests: { cpu: 100m, memory: 40Mi, ephemeral-storage: 5Mi }
            limits: { cpu: 500m, memory: 50Mi, ephemeral-storage: 10Mi }
          readinessProbe:
            httpGet: { path: /ready, port: 5000 }
            initialDelaySeconds: 2
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /health, port: 5000 }
            initialDelaySeconds: 10
            periodSeconds: 10
          lifecycle:
            # Give kube-proxy time to stop routing to this pod before it exits,
            # so scale-down doesn't cause failed requests.
            preStop:
              exec:
                command: ["sleep", "5"]
  • 10–14

    Labels are the glue of Kubernetes. The template is the pod blueprint every replica is stamped from. The selector must match the template's labels. That's how the Deployment counts its pods, and the Service finds them through the same label. Nothing refers to pods by name.

  • 8–9

    No replicas field, on purpose. If the HPA has scaled to 5 and you kubectl apply a manifest that says replicas: 1, your apply resets it to 1 and the two controllers fight. Leaving it out gives the HPA sole ownership. The frontend sets replicas: 1 because it isn't autoscaled.

  • 20

    IfNotPresent uses the image already on the node. The image is built inside minikube and isn't in any registry, so Always would fail with ErrImagePull. With a :latest tag Kubernetes defaults to Always, so this line is required.

  • 27

    mongo is the name of MongoDB's Service. Cluster DNS resolves it to a stable IP, so pods never need to know each other's addresses.

  • 34

    Caps Node's heap at 24 MB so garbage collection runs long before the container reaches its 50Mi limit.

Lines 38–40

Requests and limits: the block that drives scaling

100m means 100 millicores, a tenth of one CPU core. Mi means mebibytes.

requestslimits
Meaning“Reserve at least this for me”“Never let me use more than this”
Used byThe scheduler, to pick a node with that much free capacityThe kernel, at runtime
CPU over it—Throttled. The pod slows down but keeps running.
Memory over it—OOMKilled. The container is killed (exit code 137) and restarted.
HPA relevanceCPU utilisation = usage ÷ requestSets the ceiling: 500m ÷ 100m = at most 500%
Seen in the run

CPU. The log printed cpu 430%/50%: each pod used about 430m against its 100m request. The 500m limit is what stopped it going above 500%.

Memory. MongoDB at a 96Mi limit was OOMKilled under peak load, which is why its limit is now 128Mi. Memory can't be slowed down like CPU, so going over the limit means the process is killed.

Why the request matters for autoscaling

The HPA target of “50%” means 50% of the request. Without a CPU request, the HPA can't compute utilisation and shows <unknown>. A small request makes scaling easy to trigger on a laptop. In production, set the request to the pod's real typical usage.

Lines 41–48

Probes: when a pod gets traffic, and when it gets restarted

ProbeWhen it fails, Kubernetes…This project checks
readinessRemoves the pod from the Service, so it gets no traffic. It is not restarted./ready: is MongoDB connected?
livenessRestarts the container./health: is the process responding at all?

Readiness is what makes scale-up safe. A new pod takes a few seconds to connect to MongoDB; without the probe the Service would send it requests immediately and they'd fail. The load test shows this as 1/3: three pods exist, one is ready.

Common mistake

Making liveness depend on the database. If MongoDB blips, Kubernetes restarts every backend pod and makes the outage worse. /health only checks the process.

Lines 16 and 49–54

Graceful scale-down

When the HPA removes a pod, this sequence runs. The 5-second preStop sleep covers a race in the middle of it.

  1. t = 0s

    The pod is marked Terminating. In parallel, the endpoint controller removes it from the Service, and the preStop hook starts sleeping.

  2. t ≈ 0–2s

    kube-proxy on every node updates its routing rules. This is asynchronous, so for a moment some nodes may still send new connections to the pod.

  3. t = 5s

    preStop ends and SIGTERM reaches Node. By now routing has caught up, so the server closes its port, finishes in-flight requests and exits.

  4. t = 20s

    If the process is still running, it gets SIGKILL. The 20s grace period includes the preStop time.

This is part of why the run had zero errors while scaling down from 5 pods to 1.

Bottom of k8s/20-backend.yaml

The Service: a stable address for changing pods

k8s/20-backend.yaml Service

apiVersion: v1
kind: Service
metadata:
  name: backend
  namespace: crud-app
spec:
  selector: { app: backend } # every READY pod with this label
  ports:
    - port: 5000             # port on the Service's virtual IP
      targetPort: 5000       # port on the pods
  • 4

    The Service gets a stable virtual IP and the DNS name backend, which nginx uses in proxy_pass http://backend:5000.

  • 7

    As the HPA adds and removes pods, the Service's list of ready pods updates automatically. Nothing else needs reconfiguring. That's what makes horizontal scaling transparent to callers.

Balancing is per connection

kube-proxy picks a pod when a TCP connection opens. A client that holds one keep-alive connection stays on one pod, even after new pods arrive. So nginx.conf deliberately opens a new upstream connection per request, which is how the run reached all 5 pods.

PART 3

Autoscaling

k8s/30-backend-hpa.yaml

The HorizontalPodAutoscaler

k8s/30-backend-hpa.yaml

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: backend
  namespace: crud-app
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: backend
  minReplicas: 1
  maxReplicas: 5 # worst case 5 x 50Mi = 250Mi of backend memory
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50 # % of the 100m CPU request
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Percent # at most double every 15s...
          value: 100
          periodSeconds: 15
        - type: Pods # ...or add up to 2 pods, whichever is more
          value: 2
          periodSeconds: 15
      selectPolicy: Max
    scaleDown:
      # The Kubernetes default is 300s. 60s makes the demo quicker while
      # still avoiding flapping when load briefly dips.
      stabilizationWindowSeconds: 60
      policies:
        - type: Percent
          value: 50
          periodSeconds: 15
  • 7–10

    scaleTargetRef names the workload to scale: the backend Deployment.

  • 11–12

    The replica count is always clamped to this range.

  • 14–19

    A Resource metric is built-in CPU or memory, read from metrics-server. Utilization means a percentage of the request; the alternative AverageValue takes an absolute amount such as 200m. The target is an average across all pods.

  • 20–38

    behavior limits how fast the count can change. The next section covers it.

How the decision is made

The formula, then the brakes

Every 15 seconds the HPA controller computes:

desiredReplicas = ceil( currentReplicas × currentUtilization ÷ targetUtilization )

If that ratio is within 10% of 1.0, it does nothing. This tolerance stops jitter. Then behavior applies two kinds of brake:

SettingScale upScale down
Stabilisation window0s: act on the newest recommendation now60s: use the highest recommendation from the last 60s
Policies+100% or +2 pods per 15s−50% per 15s
selectPolicyMax: whichever allows the bigger changeMax (default)
Rounding of the policy limitUpDown
Kubernetes default if omitted0s window; +100% or +4 pods per 15s300s window; −100% per 15s

The asymmetry is deliberate. Scaling up slowly costs errors and latency; scaling down slowly only costs a little spare capacity. The scale-down window stops flapping: a single quiet 15-second stretch can't remove pods that will be needed again a moment later.

Your run, step by step

Every replica change in the run follows from the formula and the policies above.

1 → 3~60s · 30 users

Scale up, limited by the policies

  1. Formula: ceil(1 × 326 ÷ 50) = ceil(6.52) = 7 pods wanted.
  2. Percent policy: ceil(1 × 2) = 2. Pods policy: 1 + 2 = 3.
  3. selectPolicy: Max allows 3, so the result is min(7, 3) = 3.
3 → 5~80s · 60 users

Scale up, limited by maxReplicas

  1. Formula: ceil(3 × 326 ÷ 50) = 20 pods wanted.
  2. Percent policy: 3 × 2 = 6. Pods policy: 3 + 2 = 5. Max allows 6.
  3. Capped at maxReplicas: 5.
5 → 2~410s · idle

Scale down, after the window

  1. CPU fell to 3% around 360s, so the formula says 1 pod.
  2. The 60s window has to see 1 as the highest recommendation before it acts: around 410s.
  3. The 50% policy limits the step: 5 × 0.5 = 2.5, rounded down to 2.
2 → 1~420s · idle

Next 15-second period

  1. 2 × 0.5 = 1, which equals minReplicas. The run ends.

    Why the CPU column stayed stuck

    The HPA reacts to the recent past

    Several hops separate a busy pod from a new replica, and each adds delay:

    kubelet measures CPUcontinuous
    →
    metrics-server scrapesevery ~15–60s
    →
    HPA evaluatesevery 15s
    →
    New pod startsimage + boot
    →
    Readiness passesDB connected

    That's why the log repeated 326% over several rows, and why scale-down began about 50 seconds after load stopped. It also explains the MongoDB OOM: the backend reached 5 pods, each opening database connections, faster than anything else could adapt.

    Why CPU and not memory

    Node.js holds on to memory after a burst, so a memory-based HPA would scale up and never scale down. CPU rises and falls with request load, which makes it the right signal for a stateless API.

    What not to autoscale: the database

    MongoDB is stateful, so it runs as exactly one replica with its own volume.

    k8s/10-mongo.yaml excerpt
    
kind: PersistentVolumeClaim
metadata:
  name: mongo-data
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests: { storage: 50Mi }
---
kind: Deployment
metadata:
  name: mongo
spec:
  replicas: 1
  strategy:
    type: Recreate # a single RWO volume can't be mounted by two pods at once
  template:
    spec:
      containers:
        - name: mongo
          image: mongo:7
          args:
            - --wiredTigerEngineConfigString=cache_size=16M,log=(file_max=2MB,prealloc=false)
            - --setParameter=diagnosticDataCollectionEnabled=false
            - --maxConns=100
          resources:
            requests: { cpu: 250m, memory: 128Mi }
            limits: { memory: 128Mi }
          readinessProbe:
            tcpSocket: { port: 27017 }
    • 1–7

      A PersistentVolumeClaim asks for storage that outlives pods. When the MongoDB pod was OOMKilled, its replacement remounted the same data, so the items survived. ReadWriteOnce means only one node can mount it read-write at a time.

    • 13–14

      The default strategy, RollingUpdate, starts the new pod before stopping the old one. Two mongod processes would then fight over the same files. Recreate stops the old pod first, trading a few seconds of downtime for correctness. Scaling a database out properly needs replica sets and a StatefulSet; raising replicas would break it.

    • 20–23

      args overrides the image's CMD. The table below shows how the two sets of fields map.

    • 24–26

      Memory request equals limit: guaranteed 128Mi, never more. There's no CPU limit, so the database can burst when the backend scales out instead of becoming the bottleneck. These settings put the pod in the Burstable QoS class.

    • 27–28

      A TCP check only confirms the port accepts connections. A mongosh probe would start a Node.js process inside the container, and its memory would count against MongoDB's own limit.

    Experiments

    After each edit, run kubectl apply -f k8s/, then python loadtest/load_test.py --url <url> --open.

    1. Raise the target to 200%

      Set averageUtilization: 200. The backend scales later and to fewer pods.

    2. Remove the CPU request

      The HPA shows <unknown> and never scales. This proves the request is the denominator.

    3. Drop the scale-down window to 0

      Set stabilizationWindowSeconds: 0 under scaleDown. It scales down faster but may flap between load stages.

    4. Starve the backend of memory

      Set the memory limit to 30Mi. describe pod shows OOMKilled and restarts.

    5. Turn on upstream keep-alive

      Add keepalive 16; to an upstream block in nginx.conf. “Pods hit” stays low after scale-up, which shows balancing is per connection.
